# 功能对齐推进规则

本规则适用于按 Windows Desktop 版本维护的功能矩阵。矩阵是范围和状态的主入口，实施按完整页面和用户流程组织，不按单个控件或独立移动版设计拆分。当前目标为 [v2.2.7](windows-desktop/v2.2.7/matrix.md)，固定上游 commit 为 `fedc6f208aa2bd54c1019227214568083f6380ad`，遵循“先复制目标实现，再做必要适配”。v2.2.1 是冻结历史基准，不能用新版本结果回填。

## 0. 不跑偏的实施口径

- 先从固定上游对象核对页面和依赖闭包，再决定复制哪些文件；不要凭当前 vendor pin 或上游 HEAD 推断目标实现。
- 页面、样式、交互和流程优先以目标源码为准直接复制；Android 适配只处理平台能力边界，不以“移动端体验”为理由重做共享 UI。
- 版本同步是每次目标版本对齐的必需项：上游客户端版本、vendored 客户端版本、Android `versionName`、About 客户端版本必须能相互核对；远端服务版本单独记录。
- 验证以 Android 交付为主：Gradle 测试、APK 构建、安装和真机 UI 流程是主要证据。Playwright 不作为 APK 交付硬门禁，浏览器测试缺失不能被写成 Android 功能未实现。
- 一个页面可能需要多个共享依赖才能保持原流程；按用户可观察的完整页面/流程组织工作单元，不把只复制了一个组件标记为页面完成。

## 1. 开工前确认事实

每个工作单元开始前必须：

1. 记录目标上游标签/SHA、实际开发分支/SHA、vendor pin 和工作区状态。区分本地引用快照与已刷新远端；不能以初始化 main 推断整个项目进度。
2. 检查相关已集成代码、未合并分支/worktree、ADR、设计契约、移动补丁和验证台账。发现其他分支已有实现时，先确认其差异及集成方式，不重复开发、不覆盖现有工作。
3. 固定比较双方，再检查具体入口、注册/gate、数据调用和平台桥。文件存在只能证明有源码，不能证明入口可达或行为等价。
4. 核对当前矩阵结论；错误先更正并注明原因。矩阵是可修正的工作记录，不是比代码和运行证据更高的事实来源。

当前文档检查快照不自动成为后续实施分支。首次实施前需对账 dev 与现有功能分支，记录选定的开发基线；后续每个工作单元记录自己的起点。

## 2. 建立工作单元

一个工作单元应对应可独立验收的行为或用户流程，并关联所有受影响的矩阵 ID。

- 同一实现涉及多行时合并处理，例如 S18/M05/D05 通知、S36/N04/N05 SSH；不能因多个 ID 重复建设同一能力。
- 大项无法一次验收时拆成明确子任务；父项只有在其承诺范围都满足后才能闭环。
- 稳定 ID 不复用。需要增加矩阵子项时分配新 ID 并保留父子/拆分关系，不静默改变旧 ID 的含义。
- 每个工作单元指定一处推进记录，可放在实际使用的 issue 或版本目录文档中，矩阵链接到它；不重复维护多套进度。

开工时在该推进记录维护一张简短执行卡，引用已有设计和证据即可，不复制整套文档。小型任务可使用会话内记录，不要求新建 Issue。至少包含：

小任务按适用项简记，可合并或省略无关字段；不影响功能状态的任务无需关联或更新矩阵，用户明确指定的记录方式优先。

```text
工作单元 / 用户可观察的目标：
关联矩阵 ID：
上游目标 / vendor pin：
绝对工作目录 / 开发分支 / base SHA / 当前 HEAD：
已有实现、设计、决定与验证证据：
具体差距及分类：
本次范围与必要依赖 / 明确后置事项：
正常流程、交互状态、失败路径和恢复行为：
验收步骤、预期结果与验证环境：
当前授权：设备操作、提交/PR/合并及适用范围：
执行状态 / 已完成 / 剩余 / 阻塞与解除条件 / 下一步：
实现提交与 PR / 验证结果与证据位置：
```

用户调整范围或授权时更新执行卡，并通知正在工作的执行者；旧计划不再作为恢复已取消工作或已撤销授权的依据。仅在基准、范围、实现或证据发生相关变化时重新核对受影响部分。

## 3. 先分类差距，再决定动作

| 分类 | 处理方式 |
| --- | --- |
| 已有实现且行为相符 | 检查证据适用性，补必要验证；不为“逐项处理”而重写 |
| 已有实现但未验证 | 先运行对应验收；发现真实缺陷再修改 |
| 版本新增或行为变化 | 对比固定版本的 API、默认值、注册及持久化变化，增量迁移 |
| 移动平台适配 | 保留目标语义和操作结果，明确触摸、键盘、系统能力与生命周期差异 |
| 已有缺陷 | 建立可复现失败和预期结果，修复后验证关联路径 |
| 已决定排除 | 保留依据，验证入口及范围隔离；若要求显示禁用，仍须实现和验收 UI |
| 证据不足 | 标待核对并继续调查，不写成未实现，也不转嫁为用户产品决策 |

复用和升级必须保留来源、许可及移动补丁；涉及 gui-extensions → gui-plugins 等变化时，核对注册、宿主接口、偏好迁移和能力过滤，不能只替换包名。

## 4. 决策边界

- 已有用户决定、ADR 和设计范围继续有效。只有明确的新决定才能改变；发现冲突时记录冲突并确认，不默默覆盖。
- 技术实现方式、代码定位、运行兼容性调查由开发过程解决，不反复询问用户已完成的工作是否要做。
- 只有改变产品范围、支持承诺或明显影响使用方式的取舍才提请用户决定。提问必须带现有行为、具体差距、可行方案、影响和推荐意见。
- 未决定的独立事项只阻塞相关工作单元；继续推进无依赖的已确定工作。
- WSL 是已确认例子：执行能力排除，但 Android 入口必须可见且禁用并说明原因。不能用“排除”将入口隐藏或将 N12 标完成。

### 4.1 范围与评审收敛

- 计划、实现和评审都必须对应执行卡中的目标与验收。新增依赖先说明：缺少它会导致哪条构建失败或哪个用户操作无法完成，再选择最小修复。
- 通用重构、测试框架、验证工具扩建和历史治理不自动加入当前任务。已后置事项继续后置；若出现真实依赖，只处理当前交付必需的部分并记录理由，产品范围变化仍按上述决策边界确认。
- 评审阻断意见须包含具体位置或操作、证据或有依据的失败路径、影响的既定验收及解决条件；可选改善标为非阻断。评审者可以指出目标未满足，不能自行重定义目标。
- 默认一轮评审、一轮定向复审；仍未收敛时，由主代理汇总未解决问题，区分真实缺陷、证据缺口和范围建议，明确处理方式后再继续。轮数是收敛触发点，不是通过条件，不绕过必需检查或独立评审。
- 复审聚焦修复和受影响路径；发现新阻断须给新证据。无相关变化时复用已有结果，不重启整套计划、测试和评审。

### 4.2 委派与交接

仅在任务需要且已获允许的情况下委派；角色和模型以当前任务约定为准。每次交接包含：

```text
执行卡位置 / 本轮目标与交付物：
绝对 worktree 路径 / 分支 / 预期 HEAD / 工作区已有修改：
允许改动范围 / 后置事项 / 当前授权：
已有证据 / 本轮验收 / 停止条件：
设备操作者 / 已知阻塞 / 下一步：
```

- 执行者先核对工作目录、分支、HEAD 和工作区状态，不从 main 推断任务分支进度；不一致时查明原因再写入。
- 同一工作树只允许一个写入者，同一设备只允许一个操作者；更换执行者需先完成停止与交接。实施续接优先复用已有上下文，独立评审保持作者与审阅者分离。
- 返回实际改动、提交/未提交状态、验证证据、剩余缺口和下一步；主代理检查这些是否满足目标。已发现的体验差异不能仅以“条件未知”搁置，应继续调查或报告具体阻塞。
- 用户中途提问默认是当前任务的沟通：简短回答后继续已授权工作；只有明确暂停、取消或改变目标时才调整执行方向。

## 5. 推进次序

| 阶段 | 优先工作与进入下一阶段的依据 |
| --- | --- |
| 0. 基线对账 | 确认实际实施分支、未合并工作和当前工具链；完成后按此基线增量推进 |
| 1. 核心闭环 | SSH/直连 → 项目/会话 → 发任务、流式响应与权限 → 断线后恢复；优先解决阻断该流程的真实问题 |
| 2. Settings 对齐 | 设置壳、搜索、服务器作用域、核心偏好和远程配置；补目标版本差异及 WSL 禁用入口 |
| 3. 工作界面补齐 | 文件、Diff、PTY、附件、Office、侧问及其他会话操作；复用已完成路径，补具体缺口 |
| 4. 实验与发行能力 | Goal/Sources 等目标能力按其 gate 接入；APK 更新等按已确定范围执行 |

阶段表示优先顺序，不要求机械串行。核心流程依赖的设置、平台桥或工作面板应提前处理；局部低耦合修复也可先完成。调整顺序需在工作记录说明依赖或阻塞理由，不能将暂缓写成永久排除。

## 6. 实施与验证闭环

1. **先定验收**：明确数据所属服务器/项目、加载/空态/禁用态、取消、失败、重试和恢复结果；对有副作用的操作明确结果不确定时如何重新查询。
2. **增量实施**：遵守现有架构与命名。共享界面及状态经平台适配边界使用 Android 能力；不因断开客户端停止远程任务，不降低指纹/TLS 校验。
3. **同步设计**：改动界面、数据来源、权限或恢复行为时，同一交付更新已有设计契约；新增设计只覆盖确实新增的行为。
4. **按风险验证**：文档检查验证链接、ID 和引用；逻辑变化运行相关单元/集成检查；平台 UI 验证实际交互；连接、安全和生命周期能力覆盖真实失败路径，并至少完成模拟器或真机端到端验证。当前优先使用无线 ADB MatePad。
5. **验证服务闭环**：涉及远程状态、模型、权限、文件、Git 或 PTY 的结论，必须有相应真实服务证据；静态探针、mock 和 APK 安装不能替代。
6. **记录证据**：写明日期、实现提交、构建标识、设备/系统、远程服务版本、步骤、预期/实际结果及证据位置；不记录凭据或敏感连接信息。
7. **针对性回归**：检查共享依赖及受影响路径；必要检查通过后，不无理由反复扩大测试。环境不足标未验证/阻塞并说明缺什么，不虚报通过。
8. **回填与交付**：更新所有关联矩阵行、设计和推进记录，列出剩余缺口。提交遵循 conventional commit；遵守仓库实际贡献与合并流程，不能把待合并分支记为已集成。

Windows 参考端与 Android 实现端证据分开。没有 Windows v2.2.7 运行环境时可继续源码级实施，但结论必须注明参考行为尚未运行核实；不能宣称完整运行等价。

### 6.1 验证投入与体验对照

- **原样复制**：核对固定来源、必要依赖、构建和目标设备体验；保留上游测试，不为搬运功能重建其测试基础设施。
- **兼容接线与 Android 适配**：验证实际改变的行为和失败路径；必要时在最小可靠边界补测试，不为断言源码存在而新增测试。
- **连接、安全、生命周期变化**：继续执行本节真实失败路径与端到端要求。上游已通过不能证明 Android 适配也通过。

界面对齐按“同状态对照 → 安装当前 APK → 实际操作 → 比较可见结果 → 修复差异 → 复验受影响路径”推进：

1. 记录两端版本、会话、视口、缩放、键盘和折叠状态；不同条件的截图不能直接作为修改 CSS 的依据。
2. 核对入口、布局和操作结果。Desktop 存在而 Android 缺失的入口，须调查数据、偏好和平台条件；源码相同不等于体验相同。
3. 展开后检查列表或空态实际可见、未被遮挡、可触摸、切换与关闭正常；DOM 存在、数量正确或 `aria-expanded` 变化均不足以判通过。
4. 覆盖安装后核对设备 APK 与实际加载的 Web 资源身份，等待资源切换完成再验收，避免拿旧缓存验证新代码。
5. 用户要求安装和真机调试时，在既有授权内自行覆盖安装、正常启动并操作验证。需要人工解锁、系统授权或物理操作时，说明已尝试的方法及最小协助事项；不自行增加“只能自然前台”等前置条件。保留应用数据，远端副作用遵守既有授权边界。

### 6.2 提交、工作树与进度

- 可说明的迁移块完成后及时形成可追踪提交，避免数百个未提交文件混入其他任务。用户要求保留未提交 diff 时按其要求执行。
- Draft PR 是提前展示可审阅成果的入口，不代表验收通过；可在部分验收待完成时创建并明确待办。Ready/合并仍须满足实际贡献流程、必需检查和当前有效授权。
- 按可独立集成的行为或必要依赖拆分交付；不为拆分创造额外治理任务。合并后在授权范围内确认主工作树安全且可快进再同步，不覆盖用户改动。
- 搬迁工作前明确目标基线并核对创建后的实际 SHA。用户要求 move 时，先确认目标完整接收，再按授权清理源端对应修改；仅复制完成应如实报告，不能称搬迁完成。不整树删除混合任务内容。
- 进度默认报告“已完成 / 剩余 / 阻塞与解除条件 / 下一步及是否需用户参与”，以实际结果代替代理活动描述。无新证据不重复长篇汇报。
- 交付附 PR/commit/合并状态、构建身份、已验证与未验收项。统计改动量时注明比较基准，区分上游复制、兼容接线、Android 专属适配、测试/工具/文档及 patch 重复文本；重叠文件不能直接相加。

## 7. 状态与闭环标准

工作单元执行状态使用：**待处理 → 核对中 → 实施中 → 待验收 → 已闭环**；已有代码可从核对直接进入待验收。任一阶段遇到依赖可标阻塞，同时保留阻塞前阶段、原因和解除条件。

这套执行状态不替代矩阵的三个维度：

- **实现状态**：已有代码、部分实现、待核对、未实现、不实现。
- **对齐策略**：对齐、适配、新增、排除、待决策。
- **验证状态**：未验证、通过、失败、不适用；局部通过必须说明覆盖边界。

只有同时满足以下条件，工作单元才能记为已闭环：

1. 所有承诺行为有可定位的实现，或者有明确排除决定；子任务没有被父项“完成”掩盖。
2. 验收覆盖对应正常、失败及恢复路径，必要检查已通过；没有将 BLOCKED、历史局部冒烟或源码存在写成完整通过。
3. 矩阵、设计、实现和证据一致；平台差异有理由，剩余工作已明确归属。
4. 实现所在分支/提交及集成状态明确；未合并成果可以记为“分支内验收通过”，但不能当作集成基线闭环。

整体版本对齐完成还要求范围内各项均闭环、跨功能核心流程通过，并清楚列出经确认的平台差异。未解决的运行门禁必须阻止“完整对齐完成”的声明。进度按已验收流程、真实差距和阻塞报告，不用矩阵行数计算完成率。

达到本次验收且必要检查通过后进入交付，不继续扩展范围。用户选择按当前成果提前收尾时，在推进记录保留该决定及未验收项；Issue 关闭不等于全部验收通过，不据此将矩阵中的未验证项改为通过。

## 8. 版本维护

当前活跃矩阵随实施更新；切换目标版本时按 [版本维护规则](windows-desktop/README.md) 冻结旧表并创建新表。实现与验证分别迁移，旧证据只有在说明仍适用的理由后才能引用。

本规则本身发生变更时，说明适用范围及原因；不能通过降低验收标准将失败项目变成通过。

2026-11-05：根据 Settings/Session 对齐任务的沟通与执行复盘，补充执行卡、范围与评审收敛、代理交接、可见结果验收及提交节奏，适用于后续对齐任务。目的是减少重复确认、范围膨胀和交接返工；既有连接、安全及真实服务验收要求继续有效。
