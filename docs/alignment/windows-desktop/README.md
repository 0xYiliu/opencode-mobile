# 按 Windows Desktop 版本追踪功能对齐

每个**实际启动对齐工作的 Windows Desktop 版本**一个目录、一份完整功能矩阵。目录名表示上游目标版本，不表示本项目发行版。第一个对齐版本明确为 **v2.2.1**；没有前版对齐表，但有现存 vendor 基线和迁移差异。当前没有必要为尚未评估的上游版本创建空表。

本索引只记录阶段摘要，逐项状态以对应矩阵为准。状态分为：

- **活跃**：当前目标，随代码与验收持续更新。默认只保留一个活跃目标。
- **冻结**：目标切换或停止对齐时留下的历史快照，可以包含未实现、未验证和已排除项；不代表全部完成。

若以后需要同时支持多个服务版本，应另外明确兼容范围和测试环境。历史矩阵存在，不等于当前 Mobile 已验证兼容对应旧版本。

## 为什么不只复制一张表

1. **两边版本必须可定位**：每份表记录 Desktop 标签和 SHA、Mobile 检查提交/发行版或构建号、维护日期、验证范围。无构建时明确写无；工作区有未提交内容时如实注明。
2. **实现与验证分别迁移**：已有代码可能继续适用，但新版本的行为契约、服务协议和平台适配可能改变，不能直接复制“通过”。
3. **历史与当前分开**：旧表表达当时的进度。不会因为当前代码新增功能，就回填旧表制造“当时已经完成”的印象。
4. **不按行数算完成率**：行的规模不同，而且盘点范围尚未完整。当前用盘点范围、已验收用户流程和主要缺口描述对齐程度；待验收单元和分母稳定后再考虑统计。

## 升级时的操作规则

日常逐项推进遵循 [功能对齐推进规则](../workflow.md)：先对账现有实现与分支，再按工作单元实施和验收。下列规则负责目标版本切换与归档。

1. 确认新的上游版本和精确 SHA；记录升级意图。
2. 冻结旧表：更新其截止日期、Mobile 实现参照和证据范围，保留未完成项；更新索引状态。Mobile 参照指被检查的代码提交，不要求填写尚未产生的文档归档提交。
3. 新建 `v<版本号>/matrix.md` 与 `baseline.md`，包含该版本完整矩阵和可定位的 Windows 基准。可以从旧表起草，稳定功能沿用 ID；新增行为用新 ID，拆分/合并记录旧 ID 映射。
4. 新表增加“相对前一基准的变化”小节，列出新增、删除、修改、待核对及其源码证据。删除项保留去向说明，不静默丢行。
5. 未重新核对的上游能力标待核对；Mobile 实现状态仅在能定位现有代码时继承。验证默认重置为未验证；复用旧证据需明确旧环境、对应提交和仍适用的理由，不声称已经在新环境运行。
6. 更新索引的活跃目标及项目范围中的版本引用。继续逐项实施、验收，补齐每行证据。

冻结后若发现历史记载错误，可修正事实并注明修正日期和原因；新代码实现不能作为修改历史进度的依据。同一目标期间的过程变化由 Git 历史保存，不再为每次提交生成副本。

## 每份矩阵必须包含

- 版本与快照身份：上游版本/SHA、记录状态、日期、Mobile 检查提交、发行版/构建、覆盖范围和运行验收边界。
- 功能行：稳定 ID、Desktop 行为、Mobile 实现状态、对齐策略、差异理由/决定依据、验证证据；推进优先级可在阶段次序统一记录。
- 尚未决定、明确排除以及 Mobile 额外能力的记录。
- 非首份矩阵的前版变化摘要及功能 ID 映射。

矩阵中的“已实现”“适配”“不实现”“新增”含义保持跨版本一致。详细源码解释和设计文档引用对应版本资料，不引用会悄悄改变语义的浮动上游分支。
